- Machine: local desk, 8 CPUs, Python 3.14.8
- screen: Screen version 5.0.2 (build on 2026-11-01 03:06:17), minimal screenrc (status line, 10000 scrollback)
- Both attached to a headless 200x50 pty that only drains output

## Findings (written after the run)

1. **Typing starves while another window floods.** All 40 samples hit the 5 s cap
   (5000 ms means no echo seen within 5 s). Two causes (🔎, from reading the code; not yet
   proven by a fix):
   - `StreamReader.readexactly()` returns without suspending when its buffer already holds
     the bytes, so the brain's keeper loop never yields to the event loop under a flood, and
     the client's key frames are not read.
   - Head-of-line blocking: every window's output shares one keeper→brain stream with up to
     4 MB in flight (`HIGH_WATER`), so an echo waits behind megabytes of the flooding
     window, which pyte parses at about 1 MB/s.
   Fix for M1: per-window credit flow control in the keeper, a yield per frame in the brain,
   and lazy parsing of hidden windows (keep their raw tail, parse when shown).
2. **Throughput is 4–4.5× slower than screen in wall time, 7–14× in server CPU.** pyte
   parses about 0.75 MB/s (`seq`, 38.9 MB in 51 s) to 1.3 MB/s (`cat`, 50 MB in 37 s).
   The cost is in the brain (Python parsing), not the keeper (a byte copy).
3. **Idle cost is nil**, the same as screen: 0.00 % of a core with 10 windows.
4. **Interactive latency without a flood is fine**: 1.4 ms median (screen 0.3 ms); nobody
   feels that.

Decision input for spec open question 5: the keeper is not the bottleneck, so a Rust
keeper would not help. If throughput must improve beyond lazy parsing, the target is the
VT parser's hot loop.
