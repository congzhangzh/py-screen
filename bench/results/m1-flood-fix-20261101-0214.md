# Speed: py-screen vs screen (2026-11-01 02:15)

- Machine: local desk, 8 CPUs, Python 3.14.8
- screen: Screen version 5.0.2 (build on 2026-11-01 03:06:17), minimal screenrc (status line, 10000 scrollback)
- Both attached to a headless 200x50 pty that only drains output

| Test | screen | py-screen | py-screen / screen |
|---|---|---|---|
| `seq 1 5000000` wall | 13.22 s | 4.30 s | 0.3× |
| `seq` server CPU | 7.55 s | 4.11 s | 0.5× |
| `cat` 50 MB coloured log, wall | 8.07 s | 2.11 s | 0.3× |
| `cat` server CPU | 2.59 s | 2.28 s | 0.9× |
| Key → echo, idle (median / p95) | 0.3 / 0.4 ms | 1.5 / 4.3 ms | |
| Key → echo, other window floods (median / p95) | 1.6 / 2.0 ms | 1.1 / 4.3 ms | |
| Idle CPU, 10 windows, attached | 0.00 % | 0.00 % | |

## Findings (written after the run)

1. **Typing during a flood is fixed**: 1.1 ms median, 4.3 ms p95 (M0 code: no echo within
   3 s; see the erratum in m0-20261101-0124). Causes fixed: per-window credit in the keeper
   (no head-of-line blocking) and a yield per frame in the brain.
2. **Floods now finish 3–4× faster than in screen**, but that is *not* a faster parser:
   screen parses every byte; py-screen parses only the last 32 KB of a flood frame
   (README "Floods"). It's the right trade for a person watching, and it costs history: the
   skipped bytes live only in the keeper's 2 MB ring buffer until scrollback (M2) reads it.
3. pyte's own speed is unchanged (~1 MB/s). It matters again only for output that is fast
   but below the flood threshold, which no test here covers yet.
4. Idle CPU is still nil; idle echo latency is still 1.5 ms (screen 0.3 ms).
